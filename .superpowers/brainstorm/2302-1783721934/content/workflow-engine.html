2. 同步执行引擎流程

// 伪代码：同步 DAG 执行

def execute_workflow(wf_id, inputs):
  dag = load_workflow(wf_id)  # 从 PG 加载 DAG 定义
  ctx = ExecutionContext(inputs)  # 初始化执行上下文
  topo = topological_sort(dag)  # 拓扑排序

  # SSE 推送：开始工作流
  emit("workflow_start", {wf_id})

  # 逐层遍历 DAG
  while topo.has_next():
    nodes = topo.next_level()  # 获取当前层所有可执行节点
    for node in nodes:
      # SSE 推送：节点开始
      emit("node_start", {node_id})
      result = execute_node(node, ctx)  # 阻塞执行
      ctx.set(node.id, result)  # 存入上下文
      # SSE 推送：节点完成
      emit("node_done", {node_id, result})
    topo.advance()

  # 获取最终输出节点结果
  output = ctx.get(output_node)
  emit("workflow_done", {output})
  save_run_history(wf_id, ctx, output)
  return output

6. 错误处理策略

节点级错误

  • 重试策略：1次自动重试
  • 超时：默认 60s（LLM 节点可配置）
  • 失败模式：继续/终止/降级

工作流级错误

  • SSE 推送错误信息到前端
  • 运行记录持久化（即使失败）
  • 提供手动重试入口

🤔 确认问题

这个工作流引擎设计看起来合理吗？特别是：

  • 同步执行 + SSE 推流 — 长任务时前端能实时看到进度
  • 变量引用语法 — {{ node_id.output_field }} 这种类似 Dify 的做法
  • 节点注册表模式 — 新增节点类型只需实现一个类 + 注册
